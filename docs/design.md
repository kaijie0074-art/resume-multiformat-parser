# 设计（design.md）

## 路由架构

见 open-source-references.md 尾图。三个原则：

1. **入口即分流**：所有失败模式（空文本层/双栏/docx 表格）在路由层显式识别，绝不"一条路走到黑"
2. **缺失即信号**：字段抽不到 = None + 降置信 + needs_manual，让下游（回退用户手动补）接住，而不是让 LLM "猜"
3. **重炮位留接口**：OcrBackend 两真实实现同接口（自托管 Paddle / 多模态 VLM 直读），几何层解决不了的版面走模型服务，未配置时显式失败

## 关键决策

### D1：双栏检测用几何而非模型
词坐标 x0 间隙 + 两侧词量门槛（≥25%）+ 页眉豁免（顶部 15% 横跨词归通栏）。覆盖主流两栏模板；三栏/杂志版面明确不在范围（生产走 PP-StructureV3 类管线，接口已留）。阈值常量与依据写在 layout.py 模块头（评审意见 #1/#2 落实项）。

### D2：为什么"缺失标 None"而不是"LLM 补全"
问题报告 RPI-002 的教训：空输入 + 下游 LLM = 模型基于岗位描述编造整份简历。字段抽取层的职责是**只陈述看到的事实**；"看起来应该有"的推断留给下游且必须有锚点校验（姊妹仓库 llm-structured-output-hardening 的 FidelityGate）。

### D3：fields 的 naive 参数（演进留档）
`extract_fields(text, naive=True)` 保留 v0.1.0 的朴素邻近启发式（无标题过滤、无二次回填）——基线复现必须用真实的历史行为，不能拿 v1.0.0 的逻辑跑基线再宣布"基线也没那么差"。这是评估诚实性的要求。

### D4：评估口径
- 字段级精确匹配：标量（name/phone/email）+ 三元组（work: company/date/desc；education: school/degree/date）+ 证书集合
- 三元组任一分量错即整条错——下游 LLM 结构化消费的真实形态
- 比较前做标点归一化（NFKC + 全角→半角）：OCR 输出的标点形态不可控，精确匹配必须容错这一维
- 分组呈现（单栏/双栏/图片型/docx）+ 错误模式分类列（评审意见 #5）

### 拒绝的替代方案

| 方案 | 拒绝理由 |
|---|---|
| 全部输入走多模态 LLM 直读 | Token 贵且慢（一页≈上千 token）；同样会幻觉；文本层完好的 60%+ 输入被过度处理 |
| tesseract 传统 OCR 管线 | 中文简历版面+表格场景的维护成本高于版面感知方案；识别质量不足 |
| 上游引入 docling 重框架 | 单文件解析路径用不到其 80% 能力，依赖树过重 |
| .doc 老格式硬支持 | POI HWPF 对合并单元格支持残缺的背景下，转换后走 .docx 路径比硬解析可靠；路由层显式拒绝给明确提示 |

## 线上闭环（生产接入说明）

1. 部署 PaddleOCR PP-StructureV3 服务 → `export RESUME_PARSER_PADDLE_URL=...`
2. needs_manual 的简历进"用户手动补全"流（产品侧表单，预填已抽字段）
3. 每周把用户修正率最高（解析错误最多的输入形态）的样本固化进语料与测试
